### Findings

#### [HIGH-1] `verify-deletion-code` upsert names a unique constraint that does not exist — account deletion cannot complete, and the deletion-code brute-force limit is inoperative

- **Location:** `supabase/functions/verify-deletion-code/index.ts:112-118` and `:142-148`; constraint defined at `supabase/migrations/20250829171446_d2ee7ebc-33f3-47a9-8795-c3cb4864a20f.sql:96`
- **Blast radius, stated before characterization:** one file, two call sites. Reaches the `user_settings` table and the authorization gate at `delete-account/index.ts:58`. Affects every account-deletion attempt by every user, and the only brute-force control on the deletion confirmation code. Does not touch transaction, account, or billing data paths.

- **What:** `user_settings` has exactly one unique constraint, and it is on **three** columns:

  ```sql
  UNIQUE(user_id, household_id, setting_key)   -- 20250829171446:96
  ```

  Both upserts in `verify-deletion-code` specify **two**:

  ```ts
  }, { onConflict: "user_id,setting_key" });   // lines 118 and 148
  ```

  PostgREST translates that to `ON CONFLICT (user_id, setting_key) DO UPDATE`. Postgres validates the conflict-target inference at plan time against a unique index on exactly those columns. No such index exists — I checked all 53 migrations for any `CREATE [UNIQUE] INDEX` or added constraint on `user_settings` and there is none. The statement should therefore fail with `SQLSTATE 42P10, "there is no unique or exclusion constraint matching the ON CONFLICT specification"` on **every** call, regardless of whether a row actually conflicts.

  Both calls discard the result — `await supabaseAdmin.from(...).upsert(...)` with no `const { error } =` — so the failure is silent. supabase-js returns errors in the response object rather than throwing, so nothing surfaces.

  Two consequences follow:

  1. **Line 142-148 never writes `deletion_verified`.** `delete-account/index.ts:58` requires that flag to be `"true"` and fresh within 10 minutes, so it returns `403 "Deletion not verified"` on every request. Meanwhile `verify-deletion-code` returns `{ verified: true }` at line 150 regardless, so the UI advances to the delete step and then fails.
  2. **Line 112-118 never increments `deletion_code_attempts`.** `currentAttempts` is therefore read as `0` forever at line 63, `if (currentAttempts >= MAX_ATTEMPTS)` at line 65 never fires, and the 5-attempt cap on a 6-digit code is not enforced. There is no other rate limit on this endpoint.

- **Why this was not caught:** the `deletion_verified` upsert was introduced in `7f00184` on **2026-07-09** — the *same commit* that introduced the chained-`.catch()` bug PR #6 fixed. The retro correctly identified that account deletion "silently never completed since 2026-07-09" and fixed one of the two defects introduced that day. The production check on 2026-07-31 (`deletion_guard_ok=1`) confirmed the RESTRICTIVE policy exists; it did not exercise the flow. PR #6's CI run reported success after collecting **zero tests in 2.6 seconds** (see MEDIUM-3), so nothing mechanical was ever going to catch it.

- **Risk:** Two distinct harms. First, the data-deletion path — the concrete control that satisfies a GDPR/CCPA erasure request and the one the previous review credited as "the harder half" — does not work, and has not worked for a month. Worse, `DeleteAccountDialog.tsx:119` calls `clearAllUserData(user.id)` *before* invoking `delete-account`, so a user who attempts deletion loses their local financial data and keeps their account and all server-side records. Second, the brute-force limiter on the deletion code is dead. Today that has no payoff, because the same broken upsert also prevents the flag from being set — but that is two defects cancelling, not a control. **The obvious fix — correcting only the `onConflict` argument — repairs the flag write and would leave a genuinely exploitable brute-force path if the counter write is not fixed with it.**

- **A caution on the naive fix:** changing `onConflict` to `"user_id,household_id,setting_key"` does **not** work. `household_id` is `NULL` for these rows, and Postgres unique indexes treat NULLs as distinct by default, so the conflict never matches, the `DO UPDATE` never fires, and duplicate rows accumulate. `verify-deletion-code:61` then uses `.maybeSingle()` and `:84` uses `.single()`, both of which error on multiple rows — putting `currentAttempts` back to `0` and breaking code lookup entirely. The correct fixes are either a partial unique index `ON user_settings (user_id, setting_key) WHERE household_id IS NULL`, or the delete-then-insert pattern `send-deletion-code/index.ts:97-112` already uses correctly for the same keys.

- **Fix:**
  1. Run **A6** to confirm or refute. This is a live-database question and I could not answer it.
  2. If confirmed: add the partial unique index, or switch both call sites to delete-then-insert.
  3. Destructure and check the error on both writes — a silently discarded `error` on an irreversible security control is what made this invisible.
  4. Move `clearAllUserData()` in `DeleteAccountDialog.tsx:119` to *after* `delete-account` returns success.
  5. Add an end-to-end test covering request-code → verify → delete. This flow has been broken for a month with no signal.

#### [MEDIUM-1] Sign-out leaves the user's financial data in `localStorage`

- **Location:** `src/hooks/useRealAuth.ts` (`signOut`); `src/lib/dataClear.ts:59` (`clearAllUserData`, never called on sign-out)
- **Blast radius:** every signed-in user on every shared or borrowed device. Client-side only; no server data exposed.
- **What:** `signOut()` calls `supabase.auth.signOut()` and shows a toast. It never calls `clearAllUserData(user.id)`. Expenses, debts, transactions, subscriptions, hero profile and savings vault remain in `localStorage` under `${user.id}_*` after sign-out. `clearAllUserData` exists and does exactly the right thing — it is simply not wired to this transition.
- **Risk:** on a shared computer, the next person can read the previous user's full budget, debt balances and transaction history straight out of DevTools without any credential. For a financial app this is the realistic version of the "stolen device" threat the deletion-code flow was built to defend against.
- **Fix:** call `clearAllUserData(user.id)` in `signOut()` before `supabase.auth.signOut()`, capturing `user.id` first.

#### [MEDIUM-2] Privacy policy misstates where financial data is stored and omits four processors, including the AI path

- **Location:** `src/pages/PrivacyPolicy.tsx:155` and `:165-175`; AI call sites `draft-budget/index.ts:136`, `categorize-transaction/index.ts:148`, `faq-chat/index.ts:338`, `generate-store-images/index.ts:101`; geo lookup `supabase/functions/_shared/geo.ts:27`
- **Blast radius:** disclosure surface for every user; no code defect and no exploit path. Posture only.
- **What:** two gaps.
  - Line 155 states, of data received from Plaid: *"This data is stored locally on your device."* That is not accurate — account and transaction records are written to Supabase Postgres (`useLocalAccounts.ts`, `useLocalTransactions.ts` write to `supabase.from(...)` whenever a session exists), and `delete-account` deletes them from 13 server-side tables. The policy tells users their bank data never leaves their device when it does.
  - The "Data Sharing and Third Parties" section lists Stripe and Plaid. It does not mention: **ai.gateway.lovable.dev → `google/gemini-3-flash-preview`**, which receives a full financial snapshot in `draft-budget` (monthly income, every budget category and amount, every debt with balance and APR, 3-month spending averages, upcoming bill names and amounts); **Resend**, which receives email addresses; **ipwho.is**, which receives the user's IP address on every checkout attempt; or **Supabase** itself as the data host.

  - The policy is dated "Last Updated: March 25, 2026", predating the AI features.
- **Risk:** a US financial-data product telling users their bank data stays on their device, while it sits in a cloud Postgres and derived figures are sent to a third-party LLM gateway, is the kind of gap that turns a routine inquiry into a bad one. **I flag posture; I do not give legal advice and this is not a legal opinion.**
- **Fix:** correct line 155, add the four processors, re-date the policy. Consider a short "How we use AI" section given that budget drafting is a headline feature.
