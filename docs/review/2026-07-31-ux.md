## UX and Accessibility Review: zeroherobudget

**Reviewed:** 2026-07-31 | **Scope:** 14 routes, unauthenticated | **Basis:** mixed — runtime-verified for public routes, **unverified for the entire authenticated app**
**Viewports:** Desktop Chrome, Tablet 768, Mobile Chrome, Small Mobile 320 (56 screenshots) | **App started:** yes, via Playwright `webServer`

### Verdict

**FAIL.** Not primarily for what I found in the UI, but because most of the product could not be reviewed at all and one critical defect makes every quality signal on this repo untrustworthy. Nine of fourteen routes render a login modal over a blank page rather than content, so the app's actual UX is unreviewed. Separately, the CI gate has been reporting success while counting zero tests.

### Findings

#### [CRITICAL] The CI quality gate is blind — every green check is meaningless

- **Where:** `.github/workflows/playwright.yml`, "Generate test summary" step
- **What:** The summary extracts test counts with `jq '[.suites[].specs[].tests[] | select(.status == "unexpected")] | length'`. Playwright nests specs one level deeper when a file uses `test.describe`, so the path matches nothing. Verified against a real report:

  ```
  workflow jq path '.suites[].specs[].tests[]' finds: 0 tests
  recursive walk finds:                               7 tests
  actual statuses: {'unexpected': 4, 'expected': 3}
  ```

  `FAILED` is therefore always `0`. The gate `if: steps.summary.outputs.failed != '0'` never fires. The run step already swallows the exit code with `|| true`. Your last green run's own log shows `const passed = '0'; const failed = '0'`.
- **Impact:** Every green check on this repo since the workflow was authored proves only that `npm ci` succeeded. **This includes PRs #2, #3, #4 and #6 — where I reported "CI green" as evidence.** That signal was worthless and I should have checked what it measured before citing it.
- **Fix:** Drop `|| true` so the step fails naturally, or fix the jq to recurse. Minimum viable: `jq '[.. | objects | select(has("status")) | select(.status=="unexpected")] | length'`. Then verify by deliberately breaking a test and confirming CI goes red.

*Outside my lane, and I'd normally hand this off in one line. Reporting it in full because it invalidates the evidence base every other reviewer relies on.*

#### [CRITICAL] Nine routes show a login modal instead of content; 4 of 7 demo-mode tests fail

- **Where:** `/dashboard`, `/transactions`, `/subscriptions`, `/reports`, `/budgets`, `/debts`, `/accounts`, `/household`, `/journey` — all viewports
- **What:** Each renders the auth modal over an empty dark page. `e2e/demo-mode.spec.ts` asserts these are reachable unauthenticated; running it gives **4 failed, 3 passed**. The 3 passing target `/budget` and `/debt-snowball`, which aren't real routes — the router defines `/budgets` and `/debts` — so those assertions are likely matching a 404 page.
- **Impact:** Either demo mode regressed and unauthenticated visitors hit a wall where they were meant to see the product, or the tests encode an intent the app abandoned and have been failing silently ever since. Both are bad; which one it is determines the fix. The blind CI gate is why nobody knew.
- **Fix:** Decide whether demo mode is still a product goal. If yes, it's broken. If no, delete the spec and the dead `/budget` and `/debt-snowball` route references.

#### [HIGH] No landmark structure anywhere

- **Where:** all 14 routes, all viewports — `nav` count is **0 on every page**; `main` is absent on `/` and `/landing`
- **What:** No `<nav>` or `role="navigation"` exists anywhere in the app. Only `/onboarding` and `/pricing` have a `<main>`.
- **Impact:** Screen reader users navigate by landmark. With none, the only way through is linear reading from the top of every page. A skip link has nothing to target.
- **Fix:** Wrap primary navigation in `<nav>` and page content in `<main>`. Largely a change to the shared layout.
- **WCAG:** 1.3.1 Info and Relationships (A), 2.4.1 Bypass Blocks (A)

#### [HIGH] `/auth` has no `<h1>`

- **Where:** `/auth`, all viewports
- **What:** "Welcome to Zero Hero" is styled as a heading but isn't one. Zero `h1` elements on the page.
- **Impact:** No document outline on the sign-in screen — the first page many users meet.
- **Fix:** Make it an `<h1>`.
- **WCAG:** 1.3.1 (A), 2.4.6 Headings and Labels (AA)

#### [HIGH] Waitlist email input has no accessible label

- **Where:** `/` — `input[type=email]`
- **What:** No `<label for>`, no `aria-label`, no wrapping label. Placeholder text only, which is not an accessible name and disappears on input.
- **Impact:** Screen reader users get an unlabeled edit field on the site's primary conversion action.
- **Fix:** Add a visually-hidden `<label>` or `aria-label`.
- **WCAG:** 3.3.2 Labels or Instructions (A), 4.1.2 Name Role Value (A)

#### [MEDIUM] Horizontal overflow at narrow widths

- **Where:** `/landing` — 52px overflow at 320px, 6px at 768px; `/onboarding` — 38px at 320px
- **What:** `documentElement.scrollWidth` exceeds viewport width, forcing sideways scrolling.
- **Fix:** Find the offending fixed-width or unwrapped element. The 6px at tablet suggests a container padding or margin miscalculation rather than one wide child.
- **WCAG:** 1.4.10 Reflow (AA)

#### [MEDIUM] Tap targets below minimum, several on primary actions

- **Where:** all viewports. Footer links `Pricing` 43×20, `Legal` 34×20, `Support` 50×20. `Sign In` on `/landing` 35×16 at mobile. Modal close 16×16. `Skip for now` 76×20 on `/onboarding`.
- **What:** All below the 24×24 CSS px minimum. `Sign In` at 35×16 is a primary action.
- **Impact:** Mis-taps on touch, and harder targets for anyone with reduced motor precision.
- **Fix:** Increase padding or set a min block size. The modal close button is the most urgent — it's the only escape from the auth modal.
- **WCAG:** 2.5.8 Target Size Minimum (AA)

#### [LOW] Two controls without accessible names

- **Where:** `/onboarding` — one `<a>`; `/pricing` — one `<button>`
- **Fix:** Add text content or `aria-label`.
- **WCAG:** 4.1.2 (A)

### Checked and clear

- Images all have `alt` attributes across all 14 routes *(runtime-verified)*
- No heading-level skips on any route that has headings *(runtime-verified)*
- No horizontal overflow on Desktop or Mobile Chrome *(runtime-verified)*

### Unable to verify

This is most of the review, and the reason for the verdict.

- **The entire authenticated product.** Dashboard, budgets, transactions, debts, accounts, subscriptions, reports, household, journey — I only ever saw the auth modal. My per-route accessibility numbers for those paths describe the modal, not the pages, and I have excluded them from findings.
- **§2 error, empty, loading states** — unreachable
- **§6 consequence and trust** — the deletion and checkout flows are exactly what this category exists for, and both sit behind auth
- **Keyboard navigation, focus management, focus traps** — not exercised
- **Colour contrast** — `@axe-core/playwright` is not installed. I did not compute contrast manually. **Recommend adding it**; it would also cover much of §3 automatically.
- **Screen reader behaviour** — requires manual testing

To review the rest, I need either working demo mode or test credentials. `e2e/fixtures/auth.fixture.ts` exists, which suggests authenticated runs are already possible.

### For other reviewers

- **Security:** `/admin`, `/admin/login`, `/admin/waitlist`, `/admin/beta-codes` are client-side routes; worth confirming the server rejects non-admins rather than relying on route guards.
- **Design:** your `design-review` skill owns visual system consistency — I deliberately didn't assess spacing, type, or component fidelity.
