# UX and Accessibility Review: zeroherobudget

**Reviewed:** 2026-08-05 | **Scope:** 34 / 34 user-facing routes in the router (15 admin, internal and legacy-redirect routes excluded per charter) | **Basis:** mixed — runtime-verified for everything in Findings; two categories code-inferred and listed as such
**Viewports:** Desktop Chrome 1280, Tablet 768, Mobile Chrome 393, Small Mobile 320 — 216 full-page screenshots plus targeted flow captures | **App started:** yes, via Playwright `webServer`

Access to the authenticated product was obtained with `seedDemoData()` from `e2e/fixtures/demo.fixture.ts`. All 20 routes behind `Layout.tsx`'s gate were reached and exercised. The previous review reached 5 of 14; this one reached 34 of 34.

**One scope limit that shapes everything below:** demo mode gets past the route gate but does not create a Supabase `user`. So every app route was reviewed with `user === null`. Anything gated on a real session — the authenticated variant of `/household`, the Stripe checkout redirect, the live billing portal, and the terminal step of account deletion — is reported as observed up to the point where the session is required, and explicitly marked where it stops. Test credentials would close this.

---

## Verdict

**FAIL.**

The product is now genuinely reviewable and it is in far better shape than the 2026-07-31 report could see. Core jobs are completable: a user can read their dashboard, add and edit transactions, plan a budget, model debt payoff, and reach every report. Empty states are unusually good — explanatory, distinguishable from failure, and mostly carrying a forward action. The account-deletion and data-clearing dialogs are among the better destructive-action flows I have reviewed: they name the specific consequence, state permanence, require two independent confirmations, and keep the commit button disabled until both are satisfied.

The verdict is FAIL on the definition-of-done §3 clause "any High open with no owner and no date." There are eight, none of which has an owner or a date. Two of them exclude whole user groups (WCAG A failures), one is a money-display defect that shows a salary deposit as a negative expense, and one is a page that promises a feature and delivers a dead end. No Critical is open.

## Findings

### [HIGH] Income renders as a negative expense; spend totals read $0 while 34 transactions are listed

- **Where:** `/transactions`, `/budgets`, `/dashboard` — all four viewports. `src/pages/Transactions.tsx:654` and `:158`; `src/lib/demoDataLoader.ts` (26 sites). Screenshot: `Desktop-Chrome/demo/_transactions.png`
- **What:** Measured every row of the August 2026 transaction table at runtime. All 34 rows render with a leading minus in destructive red — one colour across the whole column, zero positive rows. That includes both rows whose category is `Income`:

  ```
  Aug 14, 2026 | Payroll Deposit - ABC Corp | AMOUNT="-$2,900" color=rgb(226,54,54) | cat=Income
  Jul 31, 2026 | Payroll Deposit - ABC Corp | AMOUNT="-$2,900" color=rgb(226,54,54) | cat=Income
  ```

  In the same page header: `August 2026 Summary — Total Spent $0` above `Transactions (34)`. On `/budgets`: `$0 of $8,225 spent`, `Spent $0 — No transactions yet`, every Actual cell `$0`, and `Status: On Track — All categories on track`. So the app states in three places that nothing has been logged while listing 34 transactions worth thousands.

  Root cause, confirmed in source after observing it: the canonical type is `flow: 'in' | 'out'` (`src/types/transactions.ts:16`) and the UI writes those literals. `src/lib/demoDataLoader.ts` writes `'inflow'` / `'outflow'` instead, at 26 sites. At least twelve readers across six modules compare against `'in'` / `'out'` — `Transactions.tsx:654` (`flow === 'in' ? '+' : '-'`), `Transactions.tsx:158`, `useTransactions.ts:20,38,76,89,110`, `useLocalTransactions.ts:235,255`, `useBehavioralEngine.ts:78`, `BehavioralTriggerContext.tsx:120`, `ConnectorReviewModal.tsx:332`. None of them ever matches, so every transaction is treated as an outflow for sign and colour and as neither for totals.
- **Blast radius, stated before the characterization:** the wrong literal exists in exactly one file, the demo loader. A signed-in user entering transactions through the UI writes `'in'`/`'out'` and should see correct signs. I could not verify that path — no credentials — so "demo-only" is inferred from the type and the writer, not observed. What *is* observed is that demo mode is a shipped, publicly linked surface: `/` offers "Explore Demo" as the primary way to evaluate the product.
- **Impact:** Not Critical, because no user's own money is misreported. High, because the demo is the product's shop window and it currently shows a paycheck as a loss and claims zero spending against a full ledger. A prospective user reads that as a broken budgeting app. It also means the behavioural engine, account-balance updates and budget Actual columns are all computed from a predicate that never fires in demo.
- **Fix:** Change the 26 `'inflow'`/`'outflow'` literals in `src/lib/demoDataLoader.ts` to `'in'`/`'out'`. Then narrow the type at the boundary so the mismatch cannot recur — the field is already typed `'in' | 'out'`, so the loader is writing through an untyped path worth tightening.

### [HIGH] `/household` promises household management and delivers a dead end

- **Where:** `/household`, all four viewports, demo and empty states. Screenshot: `Desktop-Chrome/demo/_household.png`
- **What:** The page header reads "Household Management — Manage your shared financial household and invite family members." The body is a single card: "No households found. It looks like you don't belong to any households yet." I enumerated every `button` and `a[href]` inside `#main-content`; the only two are the footer's "Local-First" and "Legal & Privacy" links. There is no create control, no join control, no invite control, and no explanation of what would produce one.
- **Impact:** A state with no forward path and no stated reason. The user is told the feature exists, told they have none, and given nothing to do about it. This is the charter's dead-end case exactly.
- **Caveat:** verified with `user === null`. A signed-in user may well see a "Create household" button. I could not check. Either way the demo-mode presentation is a dead end, and if the control is session-gated the page should say so rather than implying emptiness.
- **Fix:** Add the create/join action to the empty state, or — if it genuinely requires an account — replace the copy with the reason and a link to sign up.

### [HIGH] Seven interactive controls sit inside an `aria-hidden="true"` container on every route

- **Where:** every one of the 34 routes, all viewports. `src/components/ChatbotWidget.tsx:214-228`
- **What:** The Zora chat panel is always mounted and carries `role="dialog"` with `aria-hidden={!isOpen}`. When closed it is hidden only by `opacity-0 scale-95 pointer-events-none` — none of which removes descendants from sequential focus navigation. I enumerated the tabbable set on `/dashboard` at all four viewports and found the same seven every time, each inside the `aria-hidden` subtree:

  ```
  BUTTON "Close chat", BUTTON "What is Zero Hero?", BUTTON "How do I set up a budget?",
  BUTTON "What's the 50/30/20 rule?", BUTTON "Should I use snowball or avalanche?",
  BUTTON "How much emergency fund do I need?", INPUT "Type your message"
  ```

  Observed live in the Chromium tab walk: focus lands on the chat input while the panel is invisible.
- **Impact:** A keyboard user tabs into controls they cannot see. A screen-reader user has been told that region does not exist, so focus moves somewhere with nothing to announce — the classic "focus disappears" failure. It also means a permanent `role="dialog"` is exposed on every page, which misrepresents the document to assistive technology.
- **Fix:** Add `inert` to `#chat-panel` when `!isOpen` (it also implies `aria-hidden` and removes pointer events), or unmount the panel when closed.
- **WCAG:** 4.1.2 Name Role Value (A), 2.4.3 Focus Order (A)

### [HIGH] Row-delete buttons on `/budgets` have no accessible name and are 16×16

- **Where:** `/budgets`, all viewports. Desktop: 25+ unnamed controls and 52 sub-24px targets on one page. Screenshots: `Desktop-Chrome/demo/_budgets.png`, `crops/b1.png`
- **What:** Each budget row carries a red trash button measured at **16×16** with an empty accessible name, plus an unnamed drag handle (`button.cursor-grab`). The audit caps its list at 25 unnamed controls and `/budgets` hit the cap; `/transactions` also hit 25, `/subscriptions` 23 at desktop and 16 at 320px.
- **Impact:** A screen-reader user hears "button" with no name, immediately adjacent to a category combobox, and activating it permanently removes a budget line. That is an unlabelled destructive control. The 16×16 size compounds it on touch. This is the single worst accessibility spot in the app.
- **Fix:** Give each row control an `aria-label` naming its object — `aria-label={`Delete ${item.name}`}` — and raise the hit area to at least 24×24 (a transparent padded wrapper is enough; the icon can stay 16px).
- **WCAG:** 4.1.2 Name Role Value (A), 2.5.8 Target Size Minimum (AA)

### [HIGH] Reflow failure at 320px and 393px; on the report routes a primary action is pushed off-screen

- **Where:** 12 of 34 routes overflow at 320px, 6 at 393px, 1 at 768px. Screenshots: `Small-Mobile/demo/_reports_available.png`, `Mobile-Chrome/demo/_reports_subscriptions.png`
- **What:** Measured `documentElement.scrollWidth - clientWidth` per route per viewport:

  | Route | 320px | 393px | 768px |
  |---|---|---|---|
  | `/reports/subscriptions` | 143px | 70px | – |
  | `/reports/available` | 108px | 35px | – |
  | `/reports/net-worth` | 105px | 32px | – |
  | `/reports/income` | 95px | 23px | – |
  | `/data-privacy` | 95px | 23px | – |
  | `/privacy`, `/terms` | 70px | – | – |
  | `/help` | 64px | – | – |
  | `/legal` | 54px | – | – |
  | `/landing` | 52px | 16px | 6px |
  | `/onboarding` | 38px | – | – |
  | `/account` | 31px | – | – |

  Two distinct causes. On the four report routes the recharts SVG sets the page width — the offending nodes are bare `<line>` elements extending past the viewport, and the chart has no scroll container of its own. On `/privacy`, `/terms`, `/legal`, `/help` and `/data-privacy` it is a single fixed-width button: "Back to Home" at 151px and "Data Management" at 176px inside a 320px page.

  The consequence is visible in `Small-Mobile/demo/_reports_available.png`: the page content occupies roughly 350px of a 428px document, and the **Export** button sits outside the 320px viewport entirely. A user must scroll sideways to find an action they have no reason to know is there.
- **Fix:** Wrap each chart in its own `overflow-x: auto` container so it scrolls within the card rather than widening the page (the transactions table already does this correctly — see "Checked and clear"). Let the "Back to Home" and "Data Management" buttons wrap or shrink below `sm`.
- **WCAG:** 1.4.10 Reflow (AA)

### [HIGH] `/auth` still has no `<h1>`; neither do `/reset-password` or `/checkout-success`

- **Where:** `/auth`, `/reset-password`, `/checkout-success`, all viewports. Screenshot: `Desktop-Chrome/demo/_auth.png`
- **What:** `document.querySelectorAll('h1').length === 0`. "Welcome to Zero Hero" is styled as a heading and is not one. Carried over from 2026-07-31 and still open.
- **Impact:** No document outline on the sign-in screen and on the page a user lands on immediately after paying.
- **Fix:** Promote each to `<h1>`.
- **WCAG:** 1.3.1 Info and Relationships (A), 2.4.6 Headings and Labels (AA)

### [HIGH] Waitlist email input on `/` still has no accessible name

- **Where:** `/`, all viewports
- **What:** Measured directly: `email id="" name="" label=NONE aria-label=NONE wrappedLabel=NO placeholder="Enter your email"`. No `<label for>`, no wrapping label, no `aria-label`. Placeholder only, which is not an accessible name and vanishes on input. Carried over from 2026-07-31 and still open.
- **Impact:** The site's primary conversion control is an unlabelled edit field for screen-reader users.
- **Fix:** Add a visually-hidden `<label>` or an `aria-label`.
- **WCAG:** 3.3.2 Labels or Instructions (A), 4.1.2 Name Role Value (A)

### [HIGH] No `<nav>` landmark on any of the 14 public routes; 6 also have no `<main>`

- **Where:** all 14 public routes, all viewports
- **What:** `nav` count is 0 on `/`, `/landing`, `/onboarding`, `/auth`, `/reset-password`, `/privacy`, `/terms`, `/legal`, `/help`, `/data-privacy`, `/pricing`, `/checkout-success`, `/accept-invite/:token`, `/install`. `main` is additionally 0 on `/`, `/landing`, `/auth`, `/reset-password`, `/checkout-success`, `/install`.
- **Partial progress since 2026-07-31:** this is no longer true app-wide. All 20 routes inside `Layout.tsx` now report `nav=2` (the sidebar `<nav role="navigation" aria-label="Primary navigation">` plus `MobileBottomNav`) and `main=1`, and the skip link works correctly. The defect is now confined to the public shell.
- **Impact:** Screen-reader users navigating by landmark have nothing to jump to on the marketing and legal pages, including `/pricing` where the purchase happens.
- **Fix:** Wrap the public header links in `<nav>` and the page body in `<main>` in whatever shared public layout these pages use.
- **WCAG:** 1.3.1 Info and Relationships (A), 2.4.1 Bypass Blocks (A)

### [MEDIUM] Closing a dialog returns focus to `<body>`, not to the control that opened it

- **Where:** every dialog tested — keyboard-shortcuts (Ctrl+/) on `/dashboard`, "End Journey" and "Reset Quest" on `/data`, all viewports
- **What:** The dialogs are otherwise well-behaved: focus moves in on open (to "Cancel" for the alert dialogs, "Close" for the shortcuts dialog), focus is genuinely trapped — I walked 9 tabs inside the deletion dialog and every stop reported `insideDialog=true` — and Escape closes them. But `document.activeElement` after Escape is `BODY` in every case, not the triggering button. The next Tab restarts from the top of the document.
- **Impact:** A keyboard user who opens and cancels a deletion dialog is thrown back to the start of the page and must tab through the whole sidebar and page to get back to where they were.
- **Fix:** Return focus to the trigger on close. Radix does this by default when the trigger is a `DialogTrigger`; these dialogs are driven by external `useState`, so pass a ref or use `onCloseAutoFocus` to restore it.
- **WCAG:** 2.4.3 Focus Order (A)

### [MEDIUM] Heading level jumps from `h1` to `h3` on 22 of 24 app routes

- **Where:** `/dashboard`, `/journey`, `/budgets`, `/debts`, `/transactions`, `/achievements`, `/data`, `/reports` and all five report sub-routes, `/household`, `/subscriptions`, `/accounts`, `/wealth`, `/account`, `/subscription`; also `/help` and `/data-privacy`
- **What:** Every one reports exactly one skip, `h1 -> h3`. No `h2` level exists on these pages.
- **Impact:** Heading-based navigation reports a structure the page does not have; users skipping by level land unpredictably.
- **Fix:** Card titles are rendering as `h3`. Either promote the first level of section headings to `h2` or set the `Card` title element to `h2` where it is the direct child of the page.
- **WCAG:** 1.3.1 Info and Relationships (A)

### [MEDIUM] Tap targets below 24×24, including `Sign In` at 35×16 and the auth modal close at 16×16

- **Where:** all viewports. Carried over from 2026-07-31, re-measured and still open.
- **What:** Measured at Small Mobile: `/landing` `Sign In` **35×16**; footer `Pricing` 43×20, `Legal` 34×20, `Support` 50×20; `/onboarding` `Skip for now` 76×20 and `Learn more` 62×15; `/auth` modal close **16×16**. Inside the app shell: `Learn about local-first privacy` 78×16 and `Legal & Privacy` 82×16 on every route, `Dismiss hint` 20×20 on `/dashboard`, and the consent checkbox in both the deletion and clear-data dialogs at **16×16**.
- **Impact:** `Sign In` is a primary action. The 16×16 consent checkbox is a required step in an irreversible flow. Mis-taps on touch, and hard targets for anyone with reduced motor precision.
- **Fix:** Set a minimum block size or add padding. The consent checkboxes and the modal close are the ones to do first.
- **WCAG:** 2.5.8 Target Size Minimum (AA)
- *(The `Skip to main content` link measuring 1×1 when unfocused is correct `sr-only` behaviour and is excluded.)*

### [MEDIUM] Destructive vocabulary is themed away from what the action does

- **Where:** `/data` — "Point of No Return" section containing "Reset Quest" and "End Journey"
- **What:** The heading over the destructive section is "Point of No Return"; the button that deletes all financial data is "Reset Quest"; the button that permanently deletes the account is "End Journey". Each has explanatory subtext ("Permanently delete your account and all associated data"), and the dialogs themselves are titled plainly ("Delete Account", "Clear Data"). But the buttons are what a user scans and clicks. Note that `src/lib/functionalVocabulary.ts:76` already defines `deleteAccount: 'Delete Account'` — `DataManagement.tsx` hardcodes the heroic strings instead of reading it.
- **Impact:** The most consequential controls in the product are the ones whose labels least resemble their effect. A user scanning for "Delete account" will not find it.
- **Fix:** Use the functional label on the button and keep the heroic phrasing as subtext, which is the pattern the rest of the app already uses via `FUNCTIONAL_COPY` / `HEROIC_SUBTEXTS`.

### [MEDIUM] "Delete Account?" is the title of two different destructive dialogs

- **Where:** `/accounts` row action, and `/data` → "End Journey"
- **What:** Deleting a bank account row opens a dialog titled **"Delete Account?"** — "This will permanently delete "Main Checking". Transactions linked to this account will lose their account reference." Deleting the user's entire Zero Hero account opens a dialog titled **"Delete Account"**.
- **Impact:** Two irreversible actions of wildly different magnitude share a title. A user who has learned that "Delete Account" means "remove this bank card" is being trained toward the wrong instinct.
- **Fix:** Rename the row dialog to "Delete this account?" or, better, "Remove *Main Checking*?".
- *(The content of both dialogs is otherwise good — see "Checked and clear".)*

### [MEDIUM] `Edit`, `Deactivate` and `Delete` sit 4px apart on every `/accounts` row

- **Where:** `/accounts`, all viewports
- **What:** Measured on the first row: `Edit 40×40 @x=1079`, `Deactivate 40×40 @x=1123`, `Delete 40×40 @x=1167` — 4px between each. All three are icon-only at equal weight; only the colour differs (`Delete` is `rgb(226,54,54)`, the other two are `rgb(17,23,23)`).
- **Impact:** A destructive action immediately adjacent to two routine ones, separated by colour alone, at touch-hostile spacing. The targets themselves are fine at 40×40; the spacing is the hazard.
- **Fix:** Separate `Delete` from the pair — a gap, a divider, or an overflow menu.

### [MEDIUM] `Paste from Connector` becomes a nameless icon button below 640px

- **Where:** `/transactions` at 393px and 320px. `src/pages/Transactions.tsx:394-397`
- **What:** The label is `<span className="hidden sm:inline">Paste from Connector</span>` and the button carries no `aria-label` — measured `aria=""` at runtime. Its two neighbours are handled correctly (`aria-label="Export transactions to CSV"`, `aria-label="Import transactions from CSV"`). Below the `sm` breakpoint the button is a bare Shield icon with no accessible name; the Small Mobile audit of `/transactions` reports it among the unnamed controls.
- **Fix:** Add `aria-label="Paste transactions from Zero Hero Connector"`, matching the pattern already used on the sibling buttons.
- **WCAG:** 4.1.2 Name Role Value (A)

### [MEDIUM] The connector import path fires three identical error toasts and names a thing the UI never explains

- **Where:** `/transactions` → "Paste from Connector"
- **What:** Clicking it reads the clipboard directly — there is no modal, contrary to what older specs assume. When the read is refused, the page shows **three copies** of "Clipboard access denied. Please allow clipboard permissions and try again." The only explanation of what a "Zero Hero Connector" is lives in a hover tooltip ("Import transactions from Zero Hero Connector"), which is unavailable on touch.
- **Impact:** The message tells the user to grant a permission without saying where, and offers no alternative even though "Import" (CSV) sits immediately beside it. The triplication reads as three separate failures.
- **Caveat:** clipboard denial is partly a headless-browser condition; a real user would normally get a browser permission prompt first. The triplication and the message wording are not conditional on that.
- **Fix:** De-duplicate the toast, and add "or use Import to load a CSV" to the message. Give the connector a one-line explanation that is not tooltip-only.

### [MEDIUM] Committing account deletion in demo mode does nothing and says nothing

- **Where:** `/data` → "End Journey", all viewports
- **What:** The dialog arms correctly — ticking the consent box and typing `DELETE` enables "Send Confirmation Code". Clicking it produces no state change, no error, no toast, no dialog transition. `handleSendCode` in `DeleteAccountDialog.tsx` opens with `if (!user?.email) return;`, and in demo mode `user` is null, so it returns silently. The only toasts present afterwards were pre-existing backup reminders unrelated to the action.
- **Impact:** A user in the app's own demo mode can reach the final commit control of the most destructive flow in the product and press it into silence. They cannot tell whether it worked, failed, or is still working.
- **Fix:** Either disable the destructive section in demo mode with an explanatory note, or have `handleSendCode` surface "Account deletion requires a signed-in account" when `user` is null.

### [MEDIUM] `/budgets` reports "On Track" and "Variance -$0" for a budget that does not exist

- **Where:** `/budgets` in the empty state, all viewports
- **What:** With no budget items: `$0 of $0 spent`, `Planned $0`, `Spent $0`, `Variance -$0 — Under budget`, `Status: On Track — All categories on track`. `-$0` is not a value. With demo data the same panel reads `Variance -$8,225 — Under budget`, using a minus sign for a favourable outcome.
- **Impact:** "On Track / All categories on track" is a positive assertion about a budget the user has not made. The `-$8,225 Under budget` pairing puts a negative sign on a good result, which is exactly the ambiguity a financial UI cannot afford.
- **Fix:** Show a neutral "No budget set yet" status when `plannedTotal === 0`. Drop the sign from Variance and let the "Under budget" / "Over budget" label carry the direction.

### [MEDIUM] Budget rows mix formatted and unformatted currency in adjacent columns

- **Where:** `/budgets`, all viewports. Screenshot: `crops/b1.png`
- **What:** In the same row, `Planned` shows a bare number (`400`, `50`, `1800` — no symbol, no thousands separator) while `Actual` immediately beside it shows `$0`. The `Category` select truncates to "Insurance &…" at desktop width.
- **Impact:** Two money columns side by side in different notations. `1800` next to `$0` invites misreading, and the missing separator hurts most on the largest numbers.
- **Fix:** Format the `Planned` input's display value as currency, or add a `$` adornment and thousands separators to match `Actual`.

### [MEDIUM] Navigating while offline yields the browser's error page, not an app offline state

- **Where:** `/transactions` at all four viewports, with the network forced offline
- **What:** The app ships an `OfflineBanner` and a PWA service worker. With the network cut, staying on `/dashboard` is fine — the page continues to render. Navigating to `/transactions` lands on `chrome-error://chromewebdata/` with an empty document.
- **Caveat, and it matters:** this was measured against the Vite **dev** server, where the service worker is generally not registered. A production build may well handle this correctly. I am reporting it because it is what I observed and I could not verify the production build; treat the severity as provisional.
- **Fix:** Confirm against a production build (`npm run build && npm run preview`) before acting. If it reproduces, add a navigation fallback to the service worker.

### [LOW] `/accept-invite/:token` silently redirects to `/auth` with no explanation

- **Where:** `/accept-invite/demo-token-123`, all viewports
- **What:** Landed on `/auth` with the standard login modal. Nothing indicates an invitation was being accepted, that the token was invalid, or that signing in will resume the invite.
- **Impact:** An invited user who clicks a stale or malformed link gets a generic sign-in screen and no way to tell what went wrong or whom to ask.
- **Fix:** Carry the invite context into `/auth` (a line of copy, as `returnTo` already does for protected routes) or show an explicit "This invitation link is no longer valid" page.

### [LOW] The "Remember me" checkbox on `/auth` has no accessible name

- **Where:** `/auth`, all viewports
- **What:** Measured `checkbox id="" label=NONE aria-label=NONE`. The visible "Remember me" text is not associated with it. The email and password inputs on the same form are labelled correctly (`label=Email`, `label=Password`), so this is an isolated miss.
- **Fix:** Give the checkbox an `id` and point the existing text at it with `<Label htmlFor>`.
- **WCAG:** 4.1.2 Name Role Value (A)

### [LOW] `$0` spent renders in destructive red on the transactions empty state

- **Where:** `/transactions` empty state, desktop. Screenshot: `Desktop-Chrome/empty/_transactions.png`
- **What:** "Total Spent **$0**" is rendered in the destructive red used for overspending.
- **Impact:** Colour is carrying a meaning the number contradicts. Spending nothing is not an error condition.
- **Fix:** Use the neutral foreground colour when the value is zero.

## Checked and clear

- **Route reachability** — all 34 user-facing routes render their own content at all four viewports; no route redirects unexpectedly except `/accept-invite/:token`, reported above *(runtime-verified)*
- **Auth gate behaviour** — with demo data cleared, `/dashboard`, `/transactions`, `/account` and `/subscription` each redirect to `/auth?returnTo=<encoded path>`, preserving the destination *(runtime-verified)*
- **Escape from the auth modal** — the 16×16 close button and the Escape key both work and both land on `/` showing "Coming Soon" with "Explore Demo" and "Notify Me". Not a dead end, contrary to the 2026-07-31 reading *(runtime-verified)*
- **Skip link** — present, focus-visible, and functional. After Tab→Enter the next Tab lands on "Draft My Budget", confirmed inside `#main-content`. It genuinely skips *(runtime-verified, Chromium, all widths)*
- **Tab order and focus visibility in the app shell** — walked 40 stops on `/dashboard`; order matched visual order, no traps, nothing scrolled out of view, and a visible focus ring on 38 of 39 (missing only on the "Financial Insights" disclosure button) *(runtime-verified, Chromium at 1280/768/393/320)*
- **Modal focus containment** — the keyboard-shortcuts dialog (Ctrl+/), the deletion dialog and the clear-data dialog all move focus in on open and hold it: 9 consecutive tabs inside the deletion dialog all reported `insideDialog=true`. Escape closes all three *(runtime-verified)*. Focus **return** is the exception, reported above.
- **§6 irreversible actions — content of the confirmations** *(runtime-verified)*. This is the category that was entirely unreachable last time, so the detail is worth recording:
  - **Account deletion** states the consequence in specific terms before any commit: "This will permanently delete your account and all associated data, including: your profile and account settings / all transactions, budget items, and debts / subscriptions and accounts / household memberships and data", followed by "This action cannot be undone." It offers a "Backup" download in the dialog, requires a consent checkbox **and** typing `DELETE`, keeps the commit button disabled until both are satisfied (verified: `disabled=true` before, `disabled=false` after), and then requires a 6-digit code emailed to the account address. Permanence is stated; no undo is claimed.
  - **Clear all data** names the exact count: "This will permanently delete **152 items** including all transactions, budget items, debts, subscriptions, and settings", offers "Download Backup First" inline, and gates "Clear All Data" behind an irreversibility checkbox (verified `disabled=true` → enabled).
  - **Bank-account row deletion** names the object and the side effect: "This will permanently delete "Main Checking". Transactions linked to this account will lose their account reference."
- **§6 money-moving actions — amount and cadence at the moment of commitment** *(runtime-verified)*. `/pricing` shows the price adjacent to the CTA and updates it with the interval toggle: selecting Monthly gives "Start 7-Day Free Trial — Try free for 7 days, then **$10/month**"; Annual gives "then **$99/year**". ## For other reviewers

- **Cross-lane, reported at length rather than handed off, because it affects evidence other reviewers cite.** Two of the four Playwright projects do not run Chrome. `devices['iPad Mini']` has `defaultBrowserType: 'webkit'` and `devices['Galaxy S III']` has `defaultBrowserType: 'webkit'`, so the projects named **"Tablet"** and **"Small Mobile"** execute in **WebKit**; only "Desktop Chrome" and "Mobile Chrome" (Pixel 5) are Chromium. Verified directly against the installed `@playwright/test`.

  This cost me real time and nearly cost a false finding. My first keyboard walk showed only 6 reachable stops out of 68 tabbable elements at Tablet and Small Mobile, which looked like a catastrophic keyboard-accessibility failure. It is not — it is Safari's default Tab behaviour. I confirmed by running the identical walk in five configurations: 1280, 768, 393 and 320 in Chromium, plus 768 with full iPad Mini mobile emulation forced into Chromium. Tab order was correct and complete in all five. **No app defect. All my keyboard findings are Chromium-only and I have marked them so.**

  What it means for the crew: the visual-regression baselines for "Tablet" and "Small Mobile" — including PR #8's Linux set — are WebKit renders being read as though they were mobile-Chrome renders. That is a defensible choice, but nothing in the config names says so; the comment block calls them viewports and calls Desktop Chrome "the reference project". Either add `browserName: 'chromium'` to those projects or rename them so the engine is visible. Whoever owns the visual-baseline PR should know which engine produced the pixels.
- **Security:** the demo-mode deletion path calls `clearAllUserData(user.id)` locally *before* invoking the `delete-account` function (`DeleteAccountDialog.tsx`). With `user` null it never runs, but the ordering — local wipe first, server call second, failure surfaced only afterwards — is worth a look given this flow's history of destroying data without deleting the account.
- **Design:** I did not assess spacing, type scale, or component fidelity. The `design-review` skill owns that. The one visual issue I am reporting (`/budgets` mixing `1800` and `$0` in adjacent columns) is here because it is a number-legibility problem, not a styling one.
- **Data/correctness:** the `'inflow'`/`'outflow'` vs `'in'`/`'out'` mismatch is a UX finding because of what the user is shown, but the fix belongs to whoever owns `demoDataLoader.ts`, and the type-boundary hardening that would prevent a recurrence is an engineering call.

## Method note

Access via `seedDemoData()` was the difference between 5 routes and 34. The charter's Method step 2 earned its place.

Two things I got wrong mid-review and corrected before writing, recorded so the next reviewer avoids them:

1. `ChatbotWidget` renders a permanently-mounted `role="dialog"`. My first modal-focus tests matched it instead of the real dialogs and produced a convincing-looking focus-trap failure that did not exist. Every modal selector in this review is `[role=dialog]:not(#chat-panel), [role=alertdialog]`.
2. I tested the keyboard-shortcuts dialog with `?` and reported it as not opening. The shortcut is **Ctrl+/** (`Layout.tsx:75`). Re-tested; it opens, traps focus, and closes on Escape.

Both were caught by re-measuring rather than by reading source, which is the same discipline that caught the WebKit issue. Contrast is the one category where my instrument was wrong and I could not fix it in time — hence the axe recommendation, which is the highest-value single addition to this project's test setup.
