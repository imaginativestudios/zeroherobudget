## Security and Privacy Review: zeroherobudget

**Reviewed:** 2026-07-30 | **Scope:** `~/Projects/zeroherobudget` @ `c990922` (main). 50 SQL migrations, 19 edge functions, 306 `src/` files, dependency audit. Static review only — no deployed environment or live database.

### Verdict

**PASS WITH CONDITIONS.** The data-access layer is genuinely well built — materially better than typical for a Lovable-generated app. RLS is enabled on all 17 tables, the Plaid access token is protected by a column-level `REVOKE`, the Stripe webhook verifies signatures, and role escalation has explicit guards. I went in expecting to find the classic permissive-RLS problem and it isn't there. The conditions are dependency freshness and a few configuration items, not the core authorization model.

### Findings

#### [HIGH] Vulnerable dependency reachable from PDF export
- **Location:** `package-lock.json` → `jspdf@4.0.0`; used in `src/lib/reportExports.ts`
- **What:** `npm audit` reports 28 vulnerabilities (1 critical, 17 high, 9 moderate, 1 low). The critical is jsPDF ≤4.2.0 — PDF injection in `AcroFormChoiceField` allowing arbitrary JavaScript execution in the generated PDF, plus a DoS via unvalidated BMP dimensions.
- **Risk:** Report exports render user-controlled strings — transaction descriptions and merchant names, which arrive from Plaid sync and CSV import rather than being typed by the user. A crafted merchant name could reach the PDF. In a shared household, one member's imported data flows into another member's export, so this isn't purely self-inflicted.
- **Fix:** Upgrade jsPDF to >4.2.0. Also run `npm audit fix` for the non-breaking set (`ws`, `yaml`, `brace-expansion`).

#### [MEDIUM] Lockfile drift and three competing lockfiles
- **Location:** `package.json:jspdf "4.2.1"` vs `package-lock.json → 4.0.0`; plus `bun.lock`, `bun.lockb`
- **What:** `package.json` pins jsPDF to an exact `4.2.1`, but `package-lock.json` resolves `4.0.0`. `npm ci` would refuse this mismatch. Three lockfiles from two package managers are committed.
- **Risk:** What CI builds and what you build locally can differ, and the difference here lands exactly on the vulnerable version. Supply-chain review becomes ambiguous when no single file is authoritative.
- **Fix:** Pick one package manager, delete the other's lockfiles, and regenerate so `package.json` and the lockfile agree.

#### [MEDIUM] `verify_jwt = false` on all 17 configured functions
- **Location:** `supabase/config.toml`
- **What:** Platform-level JWT enforcement is disabled for every function listed. I checked each one individually: all functions that need auth do enforce it in code (`getClaims`/`getUser` with a 401 path), `stripe-webhook` correctly uses signature verification instead, and the waitlist functions are public by design. So there is no current hole.
- **Risk:** The guarantee is per-function rather than structural. The next function added to this config inherits `verify_jwt = false` and is unprotected until someone remembers to hand-write the check. This is a latent problem, not an active one.
- **Fix:** Default new functions to `verify_jwt = true` and opt out only where a webhook or public endpoint requires it, as `stripe-webhook` legitimately does.

#### [MEDIUM] Wildcard CORS on money-handling endpoints
- **Location:** `Access-Control-Allow-Origin: '*'` in all 17 edge functions — notably `create-checkout`, `customer-portal`, `delete-account`, `exchange-plaid-token`
- **What:** Any origin may invoke these endpoints. Bearer tokens in an `Authorization` header are unaffected by the browser's credentialed-wildcard restriction, so `*` provides no protection here.
- **Risk:** A malicious page holding a valid token can drive checkout, portal, or account-deletion flows directly. Auth still holds, so this is an exposure-surface issue rather than a bypass.
- **Fix:** Restrict to your production origin(s) for authenticated functions; keep `*` only for genuinely public ones.

#### [MEDIUM] `has_role` execute re-granted to `anon` — regression
- **Location:** `20260112165033` revokes it; `20260605183759` re-grants: `GRANT EXECUTE ON FUNCTION public.has_role(uuid, app_role) TO authenticated, anon, service_role;`
- **What:** A deliberate hardening step was reversed five months later with no comment. `has_role` is `SECURITY DEFINER`, so an anonymous caller can probe whether any known UUID holds the admin role.
- **Risk:** Admin-account enumeration given a user ID. Low direct impact, but it identifies high-value targets.
- **Fix:** The `authenticated` grant is required — RLS policies call `has_role` as the querying role, which is almost certainly why the revoke was undone. Drop `anon` from the grant list and keep the rest.

#### [MEDIUM] `.env` committed and absent from `.gitignore`
- **Location:** `.env` (tracked); `.gitignore` has no `env` entry
- **What:** I decoded the committed key — its JWT payload is `role: anon`, ref `ukpejgrghpewwdfztryg`. All three committed values are the intended-public `VITE_` ones. **No secret is currently exposed.**
- **Risk:** The exposure is prospective. `.env` is the file people add real secrets to, and this one auto-commits to a public repo. A future `PLAID_SECRET` or `STRIPE_SECRET_KEY` lands publicly with no warning.
- **Fix:** Add `.env` to `.gitignore`, `git rm --cached .env`, and commit a `.env.example` with the key names only.

#### [LOW] Email addresses written to function logs
- **Location:** `supabase/functions/subscribe-waitlist/index.ts:35`, `:121`
- **What:** `console.log("Subscribing email to waitlist:", email)` puts PII in log storage.
- **Fix:** Log a hash or truncated form. Relevant to any deletion-request obligation, since logs are easy to overlook.

#### [LOW] In-memory rate limiter cannot hold across instances
- **Location:** `supabase/functions/categorize-transaction/index.ts:31-40`
- **What:** `rateLimitMap` is a per-isolate `Map`. Edge functions scale horizontally and cold-start, so the counter resets and is not shared.
- **Risk:** AI-cost abuse by a distributed or persistent caller. `draft-budget` relies on the upstream provider's 429 instead.
- **Fix:** Move the counter to Postgres or Redis if AI spend matters.

### Checked and clear

- **RLS coverage** — enabled on all 17 tables; every table created has a matching `ENABLE ROW LEVEL SECURITY`.
- **The `USING (true)` scare** — `20260102004713` added a blanket-`true` SELECT on `profiles`, which would have defeated the household restriction since permissive policies OR together. It was dropped in the very next migration, `20260102004845`. Not a live issue.
- **Anonymous household insert** — `WITH CHECK (true)` with no `TO` clause would have applied to `anon`. Replaced in `20260106172644` with `TO authenticated`.
- **Plaid token exposure** — `REVOKE SELECT (access_token) ON public.plaid_items FROM authenticated, anon` plus `REVOKE ALL ... FROM anon`. Column-level revocation is a notably good control, and the household-visibility policy was later dropped so only the owner's own row is reachable.
- **Stripe webhook** — `constructEvent` with `STRIPE_WEBHOOK_SECRET`, rejects missing and invalid signatures before any handler runs.
- **Account deletion** — verifies the JWT, then requires a `deletion_verified` flag within a 10-minute window, revokes Plaid items, and cascades across 13 tables. Satisfies a data-deletion path.
- **Privilege escalation** — roles live in a separate `user_roles` table rather than a column on `profiles`, `has_role` is `SECURITY DEFINER` with `SET search_path`, and there is no UPDATE policy on `user_roles`. Owner-role escalation guards were added in `20260709184322`.
- **Billing tamper protection** — the `prevent_profile_subscription_field_changes` trigger blocks user edits to `stripe_customer_id`, tier, status, amount, and end date.
- **XSS** — no `dangerouslySetInnerHTML` anywhere in `src/`.
- **IDOR / cross-tenant** — the newest migration closed the `household_id` insert gap on six tables, requiring `private.user_in_household(household_id)` on both INSERT and UPDATE.

### Unable to verify

RLS conclusions are derived by replaying 50 migrations in filename order, not by querying `pg_policies` on the live database. If any policy was ever changed through the Supabase dashboard, the deployed state differs from what the repo shows. Worth confirming against production before you treat this as a clean bill:

```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies where schemaname = 'public' order by tablename;
```

I also could not exercise anything at runtime, so rate limits, the beta-code redemption flow, and the invitation token lifecycle were reviewed as code only.

---

Two notes on the process rather than the product. First, the charter says *"Missing or permissive RLS on tables holding user data is Critical"* — I found three constructs that would have qualified, and all three had already been fixed in later migrations. Reading the migration history chronologically rather than grepping for patterns is what distinguished those, and it's the difference between this report and a false-alarm one.

Second, the `has_role` finding is the kind only a chronological read surfaces: a security fix that was silently reverted months later. That's a good candidate for the retro-facilitator's watch list if you run it — a revoke-then-regrant with no explanatory comment is a process gap, not just a code one.
